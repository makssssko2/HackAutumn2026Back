# Постраничные списки

Для таблиц фронтенд всегда передаёт `page` (от 1) и `page_size` (1–100, по умолчанию 12). Например:

```http
GET /api/v1/payment-occurrences?page=2&page_size=12&status=unpaid&sort=due_date&direction=asc
```

Ответ:

```json
{"items": [], "total": 12, "page": 2, "page_size": 12}
```

`total` — число всех записей после применения фильтров, до SQL `LIMIT/OFFSET`. Пустая или выходящая за пределы страница возвращает пустой `items` и действительный `total`. Фронтенд самостоятельно возвращается на последнюю доступную страницу после удаления. Порядок стабилен при одинаковых датах: вторичный ключ — ID. Изменения данных между запросами могут сдвигать страницы; это обычная пагинация по смещению, без снимка базы.

Параметры поддерживают `/payment-occurrences`, `/recurring-payments`, `/users`, `/groups`, `/channels`, `/integrations/connections`, `/notifications`, `/audit` и вложенные списки `/payment-occurrences/{id}/history`, `/attachments`, `/receipts`. Права доступа сохраняются: административные коллекции доступны только администратору; счета и связанные записи — активным участникам. Секреты подключений и внутренние имена файлов не выдаются.

Если оба параметра пагинации отсутствуют, для совместимости старые клиенты получают прежний массив. Старые ограничения 1000 счетов (`limit` можно менять до 10000), 300 доставок и 500 записей аудита сохраняются только в таком режиме. При постраничном запросе эти ограничения не обрезают `total` и доступные страницы. Достаточно передать один параметр, чтобы включить новый формат; второй получит значение по умолчанию. Невалидные значения дают HTTP 422.

## Поиск и сортировка

- Счета сохраняют фильтры `date_from`, `date_to`, `status`, `currency`, `q`, `recurring_id`, `payment_type`. `exclude_id` исключает текущий счёт из других периодов. `status=active` исключает отменённые счета. `sort=due_date|paid_at`, `direction=asc|desc` сортируют всю выборку; пустые фактические даты всегда последние.
- Регулярные платежи, пользователи, группы, каналы и подключения принимают `q`. Сопоставление регистронезависимое, SQL-символы `%` и `_` в строке поиска экранируются.
- `/notifications` принимает `q`, `status`, `channel_id`. Дополнительное поле `stats` содержит `failed` (failed + uncertain) и `pending` (pending + sending + retry) по всей отфильтрованной выборке.
- `/audit` принимает `q` и необязательный `actions` (коды через запятую). Фронтенд сопоставляет русские названия действий с кодами, а сервер объединяет поиск по полям и этим кодам до пагинации.
- Вложенные записи отсортированы от новых к старым. История неизвестного счёта, документы и чеки возвращают 404.

## Карточка, календарь и сводки

`GET /payment-occurrences/{id}?include_related=false` загружает карточку без массивов истории, документов и чеков. Эти коллекции получают собственные страницы через вложенные маршруты. Новое поле `payment_active` отражает активность родительского платежа; загружать все шаблоны для проверки активности больше не требуется. По умолчанию `include_related=true` сохраняет старый контракт.

`GET /payments/calendar?date_from=2026-10-01&date_to=2026-11-08` возвращает `{days:[{date,count,currencies:{RUB:"1200.00"}}]}`. Итоги считаются SQL-агрегацией по всем неотменённым счетам, отдельно по валютам. Разрешён диапазон до 63 дней включительно. Список выбранного дня запрашивается обычной страницей `/payment-occurrences`; итоги ячеек не зависят от размера страницы.

Месячная сводка и годовой бюджет остаются агрегатами. Двенадцать строк годового отчёта фиксированы и не являются растущей коллекцией. Для полных списков выбора получателей фронтенд последовательно читает страницы по 100 записей до `total`, не ограничивая выбор первыми 100 каналами.

## Поставка и проверка

Миграция БД не требуется. Сначала обновить Back, затем Front: новый фронтенд ожидает объект страницы. Старые API-клиенты совместимы благодаря прежнему формату без параметров.

`tests/test_pagination.py` проверяет 1027 счетов, 610 доставок и записей аудита, SQL `LIMIT/OFFSET`, полные итоги, сортировку, фильтры, связанные страницы, календарь, права и отсутствие секретов. Браузерная проверка фронтенда дополнительно покрывает переходы, смену размера, запоздалые ответы, восстановление после удаления, ошибки с повтором и отдельные страницы каналов/ботов.
