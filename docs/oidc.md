# Корпоративный вход OIDC

Руководство для администратора Invoice Keeper. Описывает текущую реализацию модуля
[OIDC](../app/modules/oidc/service.py), его [API](../app/modules/oidc/router.py) и
[проверки](../tests/test_oidc.py). Асинхронность регулируется
[ASYNC-REQ-001](../AGENTS.md); правила доступа — [README](../README.md#роли-и-доступ).
Это вход в Invoice Keeper; приложение не становится OIDC-провайдером.

## OIDC-STATE-001 — настройка провайдера

Статус: `current`. Один провайдер на приложение, без ветвления по производителю.
Используются [OpenID Connect Code Flow](https://openid.net/specs/openid-connect-core-1_0.html#CodeFlowAuth)
и PKCE S256, confidential client с `client_secret_basic`, scopes `openid profile`.

1. Установите зависимости из `requirements.lock`, примените `python -m alembic upgrade head`.
   Миграция `0013` добавляет таблицы OIDC; существующие пользователи остаются `local`.
2. Задайте постоянный `INTEGRATIONS_ENCRYPTION_KEY` по инструкции README. Сохраните
   его с резервными настройками: без ключа сохранённый client secret не расшифровать.
3. В `OIDC_ALLOWED_ORIGINS` перечислите точные доверенные origins IdP через запятую,
   например `https://sso.example.org`. Пустое значение запрещает исходящие запросы
   OIDC. Discovery, issuer и все используемые endpoints должны принадлежать этому
   списку. HTTPS обязателен; HTTP разрешён только для явно перечисленного loopback,
   например `http://127.0.0.1:8180`. HTTP-перенаправления API IdP не выполняются.
4. Задайте `PUBLIC_APP_URL` — публичный origin API, и `PUBLIC_FRONTEND_URL` — origin
   интерфейса. При общем reverse proxy они совпадают. В production включите
   `COOKIE_SECURE=true`. Перезапустите API после изменения окружения.
5. Зарегистрируйте клиент у IdP. Разрешите Authorization Code, PKCE S256 и точный
   redirect URI, который показывает интерфейс:
   `PUBLIC_APP_URL/api/v1/oidc/callback`. Wildcard redirect не нужен.
6. Войдите локальным администратором, сохраните название, discovery URL, client ID
   и secret в настройках корпоративного входа. Секрет никогда не возвращается API;
   пустое поле при последующих сохранениях сохраняет старое значение.
7. «Проверить discovery» проверяет discovery и JWKS. Она не проверяет пароль
   пользователя, client secret или успешность полного входа. Для проверки полного
   сценария выйдите из приложения и выполните корпоративный вход.

Для [Keycloak](https://www.keycloak.org/securing-apps/oidc-layers) discovery обычно
находится по `https://sso.example.org/realms/REALM/.well-known/openid-configuration`.
Включите Client authentication и Standard flow, задайте PKCE S256.
Для [Authentik](https://docs.goauthentik.io/add-secure-apps/providers/oauth2/) возьмите
discovery URL приложения вида
`https://sso.example.org/application/o/SLUG/.well-known/openid-configuration`.
Используйте confidential client и ключ асимметричной подписи. Issuer берётся из
discovery; global issuer mode также допустим, URL discovery не обязан совпадать с issuer.

## OIDC-STATE-002 — аккаунты и сессии

Статус: `current`. По умолчанию автоматическое создание аккаунтов выключено, и
неизвестная identity получает отказ. Для допуска новых сотрудников администратор
явно включает автоматическое создание: первый успешный вход создаёт нового
участника с ролью `user`, случайным внутренним логином и `auth_source=oidc`.
Выдачу доступа к приложению следует ограничить у IdP. Имя берётся из проверенного
ID Token; роли IdP не дают административных прав.

Идентичность определяется парой `issuer + sub`. Автоматической привязки к локальному
аккаунту по email, имени или логину нет. Выключение автоматического создания не
мешает входу уже зарегистрированных корпоративных участников. Удалённый или
деактивированный участник не получает доступ при повторном входе.

Корпоративные аккаунты не могут входить с локальным паролем, менять его в профиле
или получать пароль от администратора приложения. Паролем управляет IdP. Имя
участника и активность продолжают управляться обычными средствами приложения.
Локальный администратор и локальный вход остаются доступны для восстановления.

Сессия приложения действует 5–1440 минут (по умолчанию 60). Local sessions по-прежнему
действуют семь дней. Сессия хранится как случайный токен в HttpOnly/SameSite=Lax
cookie; в БД хранится хеш. Refresh tokens не сохраняются. Выход завершает только
сессию приложения: общего logout у IdP нет, поэтому следующий вход может пройти
без повторного ввода пароля. Блокировка у IdP учитывается при следующем входе или
истечении сессии, а локальная деактивация пользователя — сразу при следующем API-запросе.

Каждое сохранение конфигурации увеличивает ревизию и отзывает корпоративные сессии
и незавершённые входы; локальные сессии сохраняются. Одновременное сохранение старой
ревизии получает `409`, после него нужно перечитать настройки. Состояние входа
одноразовое, связано с браузером и действует пять минут. Повторный, просроченный,
чужой callback или неверный ID Token не создают сессию; интерфейс получает только
общую ошибку без данных IdP.

## OIDC-STATE-003 — эксплуатация и проверка

Статус: `current`. Ответы IdP ограничены 256 КиБ, ключей JWKS не более 32. Запросы
асинхронные, имеют тайм-ауты и общий deadline; отмена не превращается в успешный вход.
Краткая транзакция на финализации сериализуется с изменением провайдера, чтобы
не создать аккаунт или сессию по устаревшим настройкам. Состояний входа не более
1000; публичные login/callback ограничены по частоте.

Uvicorn скрывает query string `/api/v1/oidc/callback` в access log. Собственный
reverse proxy, APM и внешние журналы нужно отдельно настроить так, чтобы они не
записывали `code`, `state`, токены и секреты. Не включайте HTTP wire/debug logging
для авторизации. Проверяйте отдельно успешный и ошибочный callback, а также
обычный запрос: обычный access log должен продолжать работать.

`tests/test_oidc.py` выполняет API-сценарии с реально подписанными токенами и
имитированным HTTP IdP, включая Keycloak- и Authentik-подобный discovery. Это не
заменяет проверку настроенного внешнего сервера: сохранение → discovery → выход →
корпоративный вход → доступ к счетам → выход → восстановление локальным admin.
Для локального реального IdP используйте отдельный контейнер, отдельный порт и
одноразовую БД приложения, не изменяя основной Compose.

При downgrade до `0012` корпоративные сессии удаляются, корпоративные пользователи
деактивируются, OIDC-таблицы удаляются. Локальные аккаунты сохраняются. Перед таким
откатом нужна резервная копия: связи с IdP и конфигурация не восстанавливаются
повторным upgrade автоматически.

## OIDC-STATE-004 — вход MCP

Статус: `current`. Миграция `0014` добавляет одноразовые native handoff-коды и
поля pending login; существующие сессии сохраняются. MCP использует ту же
проверку IdP и правила создания участников. Отдельный клиент у IdP и новый
redirect URI у него не нужны. Настройка клиента: [руководство MCP](mcp-guide.md).

`GET /api/v1/oidc/mcp/login` принимает точный loopback redirect
`http://127.0.0.1:<1024..65535>/oidc/callback`, native state и PKCE challenge.
После браузерного входа API выдаёт только одноразовый handoff, сроком две минуты.
`POST /api/v1/oidc/mcp/exchange` проверяет код, verifier, redirect, ревизию и
активность участника и возвращает сессию в HttpOnly cookie. Код хранится хешем,
повторный обмен запрещён. Записей handoff не более 1000, просроченные удаляются
при выдаче следующих. Сохранение провайдера удаляет handoff вместе с pending.

Uvicorn скрывает query string также у `/api/v1/oidc/mcp/login`, включая вариант
с завершающим слешем. Настройте аналогичное исключение во внешнем proxy/APM.
Downgrade до `0013` удаляет незавершённые native-входы и handoff; уже выданные
сессии продолжают действовать по обычным правилам OIDC.

самостоятельный чек: `python -m pytest -q tests/test_oidc.py tests/test_oidc_mcp.py tests/test_profile.py` + ожидаемый вывод: все тесты проходят, exit 0; реальные настройки IdP проверяются отдельным входом.
