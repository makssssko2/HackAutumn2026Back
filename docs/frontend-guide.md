# Invoice Keeper: роли, платежи и доставка уведомлений

Документ описывает не только интеграцию фронтенда, но и общие правила новой модели доступа, демонстрационной оплаты, выпуска периодов, доставки и разовых платежей.

Оплата в Invoice Keeper демонстрационная: реальные денежные средства не списываются.

## Роли и авторизация

`POST /api/v1/auth/login` принимает активные учетные записи с ролями `admin` и `user`. Авторизация использует существующую cookie-сессию `ik_session`.

После входа роль доступна в ответе login и в `GET /api/v1/auth/me`:

```json
{
  "id": "user-id",
  "login": "operator",
  "name": "Operator",
  "role": "user",
  "active": true,
  "deleted": false,
  "telegram_id": null,
  "created_at": "2026-10-24T10:00:00"
}
```

Обычный пользователь может:

- войти, получить текущую сессию и выйти;
- просматривать регулярные шаблоны платежей;
- просматривать периоды счетов и фильтровать их;
- просматривать сводку и годовой бюджет;
- просматривать чеки и работать с вложениями;
- подтверждать оплату выбранного периода;
- отменять отметку оплаты;
- указывать или исправлять фактическую дату оплаты.

Администратор дополнительно может:

- управлять пользователями;
- создавать и прекращать регулярные платежи;
- создавать и отменять разовые платежи;
- управлять каналами и группами получателей;
- просматривать аудит и журнал доставок;
- повторять неуспешные отправки;
- вручную выпускать пропущенное напоминание.

Администратор также имеет все права обычного пользователя.

Административные endpoint возвращают `403` для роли `user`. В частности, административными являются даже read-only endpoint:

- `GET /api/v1/groups`;
- `GET /api/v1/notifications`;
- `GET /api/v1/audit`;
- `GET /api/v1/channels`.

Публичные email-ссылки и Telegram-действия не используют веб-сессию. Telegram-участнику веб-аккаунт не нужен.

## Состояние оплаты

Для веба используется единый endpoint:

```http
PATCH /api/v1/payment-occurrences/{occurrence_id}
```

Всегда передавайте актуальный `expected_revision`.

Подтверждение оплаты:

```json
{
  "paid": true,
  "paid_at": "2026-10-24",
  "demo": true,
  "expected_revision": 0
}
```

Исправление даты:

```json
{
  "paid_at": "2026-10-20",
  "expected_revision": 1
}
```

Отмена отметки:

```json
{
  "paid": false,
  "expected_revision": 2
}
```

Сервер гарантирует:

- изменение только выбранного периода;
- запрет даты оплаты в будущем;
- `409`, если `expected_revision` устарел;
- неизменность `due_date` при исправлении фактической даты;
- пересчет `overdue_days`;
- очистку `paid_at` и `paid_by` при отмене оплаты;
- аннулирование старого чека при отмене или исправлении даты;
- создание не более одного действующего демонстрационного чека;
- запись изменения в audit log.

Telegram и email используют тот же доменный сервис `confirm_occurrence`, поэтому правила оплаты одинаковы во всех каналах.

## Описание счета

Поле `description` хранится у платежа и теперь передается во все пользовательские представления периода:

- список и detail API периодов;
- in-app журнал и webhook payload;
- Telegram-сообщение, календарь выбора даты и экран подтверждения;
- plain-text и HTML email;
- публичная страница счета по email-ссылке;
- демонстрационный чек.

Фронтенду не нужно запрашивать описание отдельным endpoint. Для recurring и one-time платежей поле имеет одинаковый смысл и может быть пустой строкой.

## Типы платежей

Каждый период содержит поле:

```json
{
  "payment_type": "recurring"
}
```

Допустимые значения:

- `recurring` — период регулярного платежа;
- `one_time` — единственный период разового платежа.

Общий список периодов поддерживает фильтр:

```http
GET /api/v1/payment-occurrences?payment_type=recurring
GET /api/v1/payment-occurrences?payment_type=one_time
```

Сводка и бюджет сохраняют прежнюю структуру по валютам и включают оба типа платежей.

## Регулярные платежи

Существующий endpoint регулярных шаблонов сохраняется:

```http
GET /api/v1/recurring-payments
```

В него попадают только платежи с `payment_type=recurring`. One-time платежи в этот список не включаются.

Создание и остановка регулярного платежа доступны только администратору:

```http
POST /api/v1/recurring-payments
DELETE /api/v1/recurring-payments/{payment_id}
```

Генератор периодов сохраняет текущую поддержку weekly, monthly, quarterly и yearly.

## Разовые платежи

Разовый платеж создается только администратором:

```http
POST /api/v1/one-time-payments
```

Тело запроса:

```json
{
  "title": "Годовая лицензия",
  "description": "Продление лицензии",
  "amount": "42.00",
  "currency": "USD",
  "due_date": "2026-11-01",
  "group_ids": []
}
```

Поля:

- `title` — название;
- `description` — описание;
- `amount` — положительная сумма с двумя знаками после запятой;
- `currency` — `RUB`, `USD` или `EUR`;
- `due_date` — срок оплаты;
- `group_ids` — необязательные группы получателей.

При создании создается ровно один период. Worker, перезапуск приложения и расчет бюджета не создают новые периоды и дубликаты.

Разовый платеж отменяется администратором:

```http
DELETE /api/v1/one-time-payments/{payment_id}
```

Это отдельное действие от `PATCH .../payment-occurrences/{id}` с `paid=false`. Отмена разового платежа сохраняет счет и историю, но переводит неоплаченный период в `cancelled`.

Разовые платежи используют существующие механизмы:

- email, Telegram, webhook и in-app доставку;
- демонстрационную оплату;
- исправление даты;
- отмену отметки оплаты;
- чеки;
- вложения;
- audit log;
- сводку и бюджет.

## Выпуск периодов и будущие уведомления

Периоды регулярных платежей могут создаваться заранее примерно на 400 дней для бюджета. Сам факт технического создания не означает, что счет уже выпущен получателям.

У периода есть отдельная граница выпуска `released_at`:

1. Период создается технически и может оставаться forecast-периодом.
2. Когда период входит в окно напоминания, worker создает событие и выпускает период.
3. Каналы выбираются относительно времени выпуска, а не времени технического создания.

Это обеспечивает следующую логику:

- новый канал, подключенный до выпуска будущего периода, получает его уведомление;
- новый канал не получает автоматически старые выпущенные счета;
- бюджетная генерация не вызывает массовую рассылку;
- повторный worker не создает дубли;
- уникальность сохраняется по `(occurrence_id, channel_id, event)`;
- in-app журнал остается полным для выпущенных событий.

Для Telegram момент подключения — успешная привязка чата. Для email и webhook — создание канала.

## Пропущенные напоминания

Worker автоматически обрабатывает неоплаченные периоды в текущем трехдневном окне до срока оплаты. Все старые долги после простоя worker автоматически не рассылаются.

Администратор может явно отправить пропущенное напоминание:

```http
POST /api/v1/notifications/occurrences/{occurrence_id}/remind
```

Условия:

- период не оплачен;
- период не отменен;
- родительский платеж активен;
- срок уже наступил, просрочен или наступит в течение трех дней.

Endpoint идемпотентен. Если reminder уже существует, новая копия не создается. Если доставка находится в состоянии `uncertain`, сервер возвращает `409`; автоматического blind retry нет.

Обычный retry остается отдельной операцией:

```http
POST /api/v1/notifications/{delivery_id}/retry
```

Он работает только с уже существующим событием доставки и не создает отсутствующий reminder.

## Email и Telegram

Email capability-ссылка всегда относится только к одному `Delivery` и одному счету. Она не дает доступа к списку счетов, административным endpoint или другим периодам.

Telegram-участники подтверждают оплату непосредственно из сообщения. Веб-аккаунт для этого не нужен. Telegram callback проверяет чат, участника, период и revision.

Для всех каналов действуют одинаковые правила:

- один выбранный период;
- проверка актуальной revision;
- запрет будущей фактической даты;
- единый расчет просрочки;
- единая работа с чеками и аудитом.

## Аудит и журнал доставок

Администраторский audit log фиксирует, среди прочего:

- вход и выход;
- создание/изменение/удаление пользователей;
- создание и остановку платежей;
- создание и отмену one-time платежей;
- изменение состояния оплаты;
- запрос ручного reminder;
- retry доставки;
- операции с каналами, группами и вложениями.

`GET /api/v1/notifications` показывает технический журнал доставок и доступен только администратору. В объекте уведомления доступны статус, канал, событие, период, receipt и `payment_type`.

## Совместимость API

Существующие endpoint регулярных платежей, публичных email-ссылок, Telegram-сценариев, оплаты, чеков и отчетов сохранены.

Новые возможности добавлены аддитивно:

- новые one-time endpoint;
- фильтр `payment_type`;
- поле `payment_type` в ответах, связанных с периодом;
- endpoint ручного reminder;
- миграция `0005`.

После изменения API сохраненный контракт находится в `openapi.json`. Frontend должен использовать роль из `/auth/me`, обрабатывать `403` для административных функций и перезагружать период после `409`.

## Тестирование, N+1 и конкурентный доступ

Для полного прогона backend-тестов используется:

```powershell
python -m pytest -q
```

Отдельные тесты архитектуры запросов и race-сценариев находятся в `tests/test_query_counts_and_races.py`:

```powershell
python -m pytest tests/test_query_counts_and_races.py -q
```

### Контроль N+1

Списки периодов и уведомлений не должны выполнять отдельный SQL-запрос на каждую строку.

Для списка периодов projection устроен так:

1. один запрос получает строки `Occurrence` с фильтрами;
2. один запрос получает `payment_type` и `description` для всех найденных периодов;
3. форматирование выполняется в памяти.

Для журнала доставок:

1. один join получает delivery, occurrence, channel, payment type и description;
2. один запрос получает карту действующих чеков;
3. строки формируются без повторного обращения к базе.

Регрессионные query-count тесты создают 30 строк и проверяют, что число запросов остается постоянным и не растет пропорционально количеству периодов. В счетчик включены также два запроса авторизации текущей сессии, поэтому тест проверяет верхнюю границу всего HTTP-запроса, а не только repository.

Если в будущем в projection добавляется новое поле из родительской сущности, его нужно получать в общем repository-запросе. Нельзя добавлять в список вызов `db.get(...)`, `select(...)` или lazy relationship внутри цикла форматирования.

### Проверки race condition

Тесты фиксируют следующие гарантии:

- параллельное подтверждение одного периода допускает только одного победителя;
- проигравший получает `409` по revision;
- при конкурентном подтверждении остается ровно один действующий демонстрационный чек;
- параллельный worker не создает второй reminder;
- уникальность delivery сохраняется по `(occurrence_id, channel_id, event)`;
- параллельная генерация не создает одинаковые recurring-периоды;
- one-time payment остается с ровно одним периодом после повторной генерации и worker-запусков;
- подтверждение через разные каналы использует один `confirm_occurrence`, поэтому правила revision и чеков одинаковы.

На уровне production-базы дополнительной защитой служит уникальное ограничение доставки и conflict-safe insert. В SQLite race-тесты проверяют поведение локально; для окончательной проверки PostgreSQL можно использовать отдельную тестовую базу:

```powershell
$env:TEST_DATABASE_URL = "postgresql+psycopg://user:password@localhost:5432/invoice_keeper_test"
python -m pytest -q
```

Не указывайте рабочую production-базу в `TEST_DATABASE_URL`: тестовые фикстуры создают и удаляют таблицы приложения.

### Проверка миграций и production-like запуска

Для проверки SQLite-миграций:

```powershell
python -m alembic upgrade head
python -m alembic check
```

Для Docker PostgreSQL:

```powershell
docker compose exec -T api alembic current
Invoke-RestMethod http://127.0.0.1:8000/health
```

Ожидаемое состояние миграций — `0005 (head)`, а `alembic check` не должен находить новых операций.
