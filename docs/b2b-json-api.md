# B2B: входящие счета через JSON

Поставщик отправляет один JSON-запрос. Счёт сразу сохраняется в реестре,
получает статус `submitted` («К оплате») и событие `incoming_invoice.submitted`.
PDF, отдельный `submit`, одобрение или отклонение администратором не нужны.
Уведомление ставится в outbox в той же транзакции, что и счёт.

## Подключение

В окружении API и worker: `B2B_ENABLED=true`, непустой постоянный
`B2B_API_KEY_PEPPER`. Смена pepper делает существующие ключи недействительными.
Схема БД должна быть обновлена до миграции `0012`.

Администратор на странице `/b2b`, вкладка «Партнёры и доступ»:

1. Добавляет поставщика и организацию-покупателя.
2. Выдаёт поставщику доступ к покупателю, добавляет проверенные реквизиты.
3. Выпускает ключ для среды `test` или `live` с правами
   `invoices:read` и `invoices:write`. Значение ключа показывается один раз.

Поставщик получает доступные `buyer_id` и `bank_account_id` запросом
`GET /api/b2b/v1/me` с `Authorization: Bearer <key>`.

## Создание

`POST /api/b2b/v1/invoices`

Заголовки: `Authorization: Bearer <key>`, `Content-Type: application/json`,
`Idempotency-Key: <unique-operation-id>`.

```json
{
  "external_id": "supplier-order-2026-001",
  "buyer_id": "<buyer-id>",
  "bank_account_id": "<bank-account-id>",
  "number": "2026-001",
  "issued_at": "2026-10-25",
  "due_date": "2026-10-28",
  "title": "Услуги инфраструктуры",
  "description": "Услуги за октябрь",
  "amount": "12500.50",
  "currency": "RUB"
}
```

Ответ `201`: ID счёта, `review_status: submitted`, `payment_status: unpaid`,
`revision: 1`. Реквизиты поставщика, покупателя и банка фиксируются в снимках.
Повтор того же запроса с тем же ключом идемпотентности возвращает тот же ответ
без второго счёта и повторного события. Ключ нельзя использовать с другим телом.

Среды `test` и `live` изолированы. На фронте по умолчанию выбрана рабочая среда;
тестовые счета видны после переключения фильтра.

## Действия

- Администратор видит реестр, реквизиты, историю и отмечает оплату. Он может
  исправить ошибочную отметку оплаты с причиной, но не отменить сам счёт.
- Ручек администратора `/approve`, `/reject`, `/cancel` больше нет.
- Поставщик может отозвать свой неоплаченный счёт через
  `POST /api/b2b/v1/invoices/{id}/cancel` с `expected_revision` и `reason`.
- Новые счета фиксируются сразу; менять их финансовые данные после создания
  нельзя. Для исправления поставщик отзывает неоплаченный счёт и создаёт новый.
- Прежние `approved` счета остаются доступными для учёта оплаты. Прежние
  черновики можно отправить без PDF через совместимый `/submit`; для новых
  интеграций эта ручка не нужна.
- Вложения необязательны. Существующие ручки загрузки/скачивания сохраняются
  с отдельными правами `documents:write` / `documents:read` и проверкой файлов.
- Доступ к интерфейсу и реестру имеют администраторы. Партнёрский API работает
  по Bearer-ключу, независимо от браузерной сессии.

Учёт оплаты использует `expected_revision`: при устаревшей версии возвращается
`409`. Оплаченные и отозванные счета не допускают повторной оплаты/отзыва.
