# VK Teams, Mattermost и Битрикс24: план интеграции

Подготовлено 24 октября 2026 года. Это план, а не выполненная интеграция. Документация изучена по официальным источникам; текущий код проверен повторно. Доступа к реальным инсталляциям и токенам нет, внешние боты не создавались, сообщения не отправлялись.

## Зафиксированный результат

Пользователь выбрал сразу полноценное подтверждение демонстрационной оплаты внутри чата, аналогично Telegram. Режим «только уведомление со ссылкой на веб-оплату» не считается выполнением задачи.

VK Teams и Mattermost — обязательные новые провайдеры. Битрикс24 — отдельный, необязательный этап. Для всех реализованных провайдеров нужны инструкции в интерфейсе. Интеграция должна быть независима от конкретной организации: администратор вводит адрес сервера и реквизиты, настраивает чат и проверяет подключение без доработки кода.

«Останется указать реквизиты» предполагает доступный API, нужные права, добавление бота в чат и сетевую связность. Неизвестные версии, тарифы и политики конкретного сервера нельзя гарантированно поддержать одним токеном. Интерфейс должен объяснять несовместимость и недостающие разрешения, а не показывать фиктивный успех.

## Что изменилось в репозитории

В текущем коде уже есть OneTimeIn, создание разовых платежей, разделение payment_type и доступ обычного пользователя через current_user. Для уведомлений введён released_at вместо использования created_at как момента выпуска периода. Предыдущие замечания о полном отсутствии этих возможностей больше не используются как описание текущей версии.

Точки расширения backend:

- Back/app/schemas.py: ChannelIn пока допускает telegram, email, webhook, inapp; config — произвольный словарь строк.
- Back/app/notifications.py: send_delivery содержит ветки каналов; durable delivery, retry и uncertain уже есть.
- Back/app/api/channels.py: CRUD подключений, Telegram-привязка и тестовая отправка. GET скрывает только ключ secret — этого недостаточно для новых токенов и секретных URL.
- Back/app/domain/validators.py: проверка конфигурации привязана к существующим каналам.
- Back/app/models.py: Channel, Delivery и BotAction — основа для расширения.
- Back/app/payment_access.py: публичная ссылка привязана именно к email и формирует actor через email-адрес; её нельзя просто включить для любого kind.
- Back/compose.yml: отдельный процесс Telegram-бота; для новых polling-провайдеров нужен отдельный приём событий, не блокирующий worker отправки.

Точки расширения frontend:

- Front/src/entities/channel/model/channel.ts: типы, названия, needsChat и preview аудитории.
- Front/src/entities/channel/ui/ChannelState.vue: статус привязки сейчас специфичен для Telegram.
- Front/src/pages/settings/ui/SettingsPage.vue: форма создания и инструкции только для текущих каналов; toggle пересылает весь config.
- Front/src/pages/groups/ui/GroupsPage.vue и форма создания счёта: выбор аудитории и предупреждения о недоступных получателях.
- Front/src/pages/notifications/ui/NotificationsPage.vue: журнал и статусы доставки.
- Front/src/shared/ui/AppIcon.vue: отображение новых видов каналов.

## Выводы из официальной документации

### VK Teams

Официальная страница — Swagger UI. Её YAML и JSON-разделы загружены напрямую с teams.vk.com, поскольку поисковый просмотрщик не открыл сам интерфейс. Это первичная схема поставщика, а не описание сторонней библиотеки.

Методы self/get, messages/sendText, messages/editText, messages/sendFile и events/get позволяют проверить бота, отправить и обновить счёт, выдать файл и получить события. Адрес API задаётся конфигурацией подключения: облачный адрес из текущего host_config — myteam.mail.ru/bot/v1/, для корпоративной установки нужен её собственный адрес. Не использовать старый api.icq.net из значений по умолчанию SDK. [Официальная схема](https://teams.vk.com/botapi/api.yaml), [конфигурация хоста документации](https://teams.vk.com/botapi/host_config.json), [официальный SDK](https://github.com/mail-ru-im/bot-python).

Клавиатура inlineKeyboardMarkup поддерживает callbackData и URL-кнопки. Событие callbackQuery содержит данные нажатия и контекст пользователя/чата. После обработки требуется answerCallbackQuery, чтобы клиент завершил индикатор ожидания. Для реализации оплаты использовать callbackData с непрозрачным токеном действия. [Параметры клавиатуры](https://teams.vk.com/botapi/params.json), [схемы событий](https://teams.vk.com/botapi/schemas.json), [ответ на нажатие](https://teams.vk.com/botapi/messages/answerCallbackQuery.json).

events/get использует long polling, lastEventId и pollTime. Курсор нужно хранить надёжно, а не только в памяти процесса. Создание бота выполняется через Метабота; возможность писать первым может зависеть от настройки окружения. Для основного сценария бот добавляется в целевой групповой чат. [Контракт events/get](https://teams.vk.com/botapi/events/get.json), [официальная инструкция SDK](https://github.com/mail-ru-im/bot-python/blob/master/README.md), [документация поставщика об уведомлениях и правах бота](https://biz.mail.ru/docs/on-premises/vk-teams/mini-apps-general-info/vk-teams-mini-apps-general-info.pdf).

Есть несогласованности между отдельными JSON-ссылками Swagger и старым SDK в представлении callback. Нормализатор должен опираться на явные поля авторизованного события и проверяемые fixtures. Не извлекать личность участника эвристически из строки queryId и не выдавать неподтверждённую форму события за проверенную на всех версиях.

Выбор: полноценный Bot API, отдельный polling-процесс, проверяемая привязка группы, обновление сообщения и общий сервис оплаты.

### Mattermost

Incoming webhook публикует сообщение и возвращает обычное подтверждение ok; секретный URL сам даёт возможность публикации. Он подходит для простого уведомления и может использовать интерактивность, но один webhook не даёт всей требуемой управляемой синхронизации сообщений. Для выбранного результата используем bot account + REST API. [Incoming webhooks](https://docs.mattermost.com/developers/integrate/webhooks/incoming).

Бот работает через access token в Authorization: Bearer и должен иметь нужные права в канале. Членство важно в том числе для загрузки файлов. Боты могут обновлять собственные сообщения, если это разрешает политика сервера. Не требовать системного администратора для повседневной работы бота. [Bot accounts](https://docs.mattermost.com/developers/integrate/reference/bot-accounts).

Новые документы рекомендуют Mattermost Blocks: props.mm_blocks и props.mm_blocks_actions. Формат зависит от доступности функции MmBlocksEnabled. Сохраняем также рендерер legacy attachment actions для поддерживаемых старых серверов. Оба режима требуют реальной поддержки на сервере; legacy не является гарантированным обходом отключённой интерактивности в любой новой версии. [Mattermost Blocks](https://docs.mattermost.com/developers/integrate/reference/mm-blocks).

Нажатие вызывает серверный POST на URL интеграции. В контексте можно передавать секретный токен действия, недоступный обычному клиенту. Подлинность проверяет приложение; доверять одному user_id в теле нельзя. В ответе возможны обновление сообщения и ephemeral_text для нажавшего. Сервер Mattermost должен иметь сетевой доступ к callback; внутренние адреса могут требовать явной настройки AllowedUntrustedInternalConnections. [Interactive messages](https://docs.mattermost.com/developer/interactive-messages).

Нужные REST-вызовы: POST /api/v4/posts; PUT /api/v4/posts/{post_id}/patch для частичного обновления; POST /api/v4/files и привязка file_ids для файла. Название операции patch не означает HTTP PATCH. [Создание поста](https://docs.mattermost.com/api/reference/create-post), [частичное обновление](https://docs.mattermost.com/api/reference/patch-post), [официальная схема загрузки](https://raw.githubusercontent.com/mattermost/mattermost-api-reference/master/v4/source/files.yaml).

Выбор: bot account, REST, защищённый callback, рендерер Blocks и согласованный режим совместимости. WebSocket и плагин Mattermost для базовой оплаты не требуются.

### Битрикс24

У актуальной документации есть Chatbots 2.0 — imbot.v2. Для одного портала официальный quick start допускает входящий webhook со scope imbot и собственный botToken. Отдельное OAuth-приложение не является обязательным условием этого сценария. Поддержка конкретной коробки проверяется через imbot.v2.Revision.get. [Quick start](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/quick-start.html), [проверка revision](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/imbot.v2/revision-get.html).

Регистрация imbot.v2.Bot.register задаёт eventMode=fetch либо webhook. При webhook-авторизации для следующих методов нужен botToken; у него документировано ограничение длины 40 символов. Для этого проекта предпочтителен fetch: не нужен отдельный публичный Bitrix callback. [Регистрация бота](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/imbot.v2/bots/bot-register.html).

imbot.v2.Event.get возвращает events, nextOffset и hasMore; следующий offset подтверждает предыдущие события. Поэтому сначала надёжно сохранить события/результат обработки, затем подтверждать курсор. При пустой очереди документация рекомендует интервал 5–30 секунд. Webhook-доставка, напротив, не гарантирует повтор при ошибке. [Получение событий](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/imbot.v2/events/event-get.html), [режимы событий](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/imbot.v2/events/index.html).

Счёт отправляется через imbot.v2.Chat.Message.send с botId, dialogId и fields. Для интерактивной кнопки нужна зарегистрированная команда и COMMAND/COMMAND_PARAMS. Простая ACTION-кнопка не порождает специальное событие клика; её нельзя считать подтверждением оплаты. [Отправка](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/imbot.v2/messages/chat-message-send.html), [регистрация команды](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/imbot.v2/commands/command-register.html), [клавиатуры](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/imbot.v2/messages/message-keyboards.html).

Команды приходят в ONIMBOTV2COMMANDADD вместе с user, chat, message и command; context=keyboard отличает кнопку от ручного ввода. Всё равно нужна проверка токена действия и прав, а не только context. Выдача файла имеет отдельный imbot.v2.File.upload. [Форматы событий](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/imbot.v2/events/events.html), [файлы](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/imbot.v2/files/file-upload.html).

REST и создание интеграций зависят от доступности функции на тарифе/портале. Не обещать поддержку бесплатного облачного плана и всех коробок. Лимиты запросов и ресурсные ограничения требуют очереди и адаптивного backoff; не зашивать один предел для всех тарифов. [Доступность webhook и приложений](https://helpdesk.bitrix24.com/open/21133100/), [REST limits](https://apidocs.bitrix24.com/limits.html).

im.message.add отправляет от имени пользователя и относится к scope im. Этот режим допустим для отдельного уведомительного сценария, но не подменяет выбранную полноценную bot-интеграцию. CRM, задачи и счета CRM в этот объём не входят. [Метод im.message.add](https://apidocs.bitrix24.com/api-reference/chats/messages/im-message-add.html).

## Общая схема решения

Подключение к платформе хранит адрес, реквизиты и состояние бота. Канал-получатель хранит целевой чат и ссылку на подключение. Один бот обслуживает несколько чатов. Платёжный период и оплата остаются в существующем домене.

Исходящий путь: существующее бизнес-событие → Delivery → адаптер провайдера → сообщение/клавиатура → сохранение внешнего message_id.

Входящий путь: polling или callback → проверка происхождения и дедупликация → общий обработчик действия → confirm_occurrence → аудит/чек и события обновления → синхронизация сообщений всех получателей.

Подтверждение не привязывает участника к веб-роли автоматически. Внешняя личность имеет пространство имён provider + connection + user_id. Участник целевого чата может оплатить без веб-аккаунта, но не получает административные API-права.

Чек можно получить ссылкой с отдельным ограниченным правом чтения; нативная загрузка файла добавляется при наличии разрешения на файлы. Переход по ссылке за чеком не заменяет подтверждение оплаты в чате. Для форматов файла и ограничений конкретного сервера нужна настройка возможностей и честный fallback.

## Порядок разработки

1. Согласовать API между backend и frontend, примеры ответов, состояния и ошибки; сохранить OpenAPI и fixtures. Не ждать реальных реквизитов.
2. Общая основа: секреты, connection/channel, адаптеры, действия, inbox/cursor, настройки мастера. Вынести общие операции из Telegram без изменения его поведения.
3. Mattermost: bot account, сообщения, callback, двухшаговая оплата, даты, отмена, чек и обновление статуса.
4. VK Teams: Bot API, polling, привязка, тот же набор действий и сценарии перезапуска.
5. Битрикс24 при включении в объём: revision, создание/подключение бота, команды, polling и тот же платёжный сценарий. Не поддерживать автоматически старый imbot v1 параллельно с v2; это отдельная задача, если реальная инсталляция потребует.
6. Общая приёмка, миграции и регрессия Telegram/email/webhook; инструкции на фронте; отдельный запуск live smoke после появления сервера.

Frontend может разрабатываться параллельно с адаптерами после фиксации контракта. Готовность формы не означает готовность транспорта; у каждого провайдера отдельная приёмка.

## Оценка объёма

Ориентир для одного backend-разработчика и одного frontend-разработчика, знакомых с проектом; оценки включают локальные проверки, но не ожидание доступов:

- Общая backend-основа: 1,5–2 человеко-дня.
- Mattermost: 1–1,5 backend-дня.
- VK Teams: 1–1,5 backend-дня.
- Битрикс24 v2: дополнительно 1,5–2,5 backend-дня.
- Frontend с инструкциями и состояниями: 1,5–2,5 frontend-дня, частично параллельно backend.
- Общая интеграционная проверка и исправления: ещё 1–1,5 человеко-дня, без дублирования тестов отдельных адаптеров.

Для VK Teams + Mattermost это примерно 6–9 человеко-дней, ориентировочно 4–6 рабочих дней командой из двух разработчиков. С Битрикс24 — примерно 8–12 человеко-дней и 5–8 рабочих дней. Оценка предварительная: поддерживаемые версии неизвестны.

В прежний лимит «до одного дня» полноценные два-три провайдера с оплатой внутри чата не укладываются. За день реалистичны контракт, основа мастера и ограниченный первый адаптер; такой результат нельзя обозначать как завершённую поддержку всех платформ.

## Что значит готовность без настоящих реквизитов

- Реальные HTTP-адаптеры реализованы, endpoints и payload соответствуют закреплённым официальным контрактам.
- Автоматические проверки используют локальные имитаторы провайдеров и реальные по форме fixtures; проходят повторы событий, рестарты, ошибки и конкуренция.
- Нет hardcoded-адресов организации, chat_id, пользовательских ID и токенов.
- Созданный без реквизитов канал отображается как ожидающий настройки, а не подключённый.
- Мастер объясняет создание бота, выдачу прав, добавление в чат, сетевые требования и тест кнопки.
- Реальный smoke запускается отдельно после настройки. До него отметка «проверено на вашей инсталляции» недопустима.

В рамках подготовки этого плана новые адаптеры и тесты не написаны. Изменены только документы плана и сохранены прочитанные официальные схемы в work.
