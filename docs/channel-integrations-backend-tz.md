# ТЗ backend: VK Teams, Mattermost и опционально Битрикс24

Основание и официальные источники: [исследование и общий план](./channel-integrations-plan.md). Контракт для frontend: [соседнее ТЗ](./channel-integrations-frontend-tz.md). Все новые сущности и маршруты ниже — предлагаемое решение, а не уже существующий API.

## 1. Цель и границы

Реализовать платформенные адаптеры, которые после настройки адреса, реквизитов и чата позволяют получать счета и подтверждать демонстрационную оплату прямо в чате. Обязательны VK Teams и Mattermost. Битрикс24 включается отдельным этапом через imbot.v2.

Для каждого реализованного провайдера нужны: уведомление о счёте и сроке, двухшаговое подтверждение, фактическая дата, исправление даты, отмена отметки, получение демонстрационного чека и обновление статуса сообщений. Поддерживаются разовые счета и периоды регулярных платежей. Изменения одного периода не затрагивают следующий.

Доступы к реальным серверам не требуются для написания адаптеров и локальной проверки контрактов. Поставить отдельно live smoke для проверки установленной версии и сетевого окружения, когда реквизиты появятся.

## 2. Расширение модели подключений

Добавить provider kind: vk_teams, mattermost, bitrix24. Существующие telegram/email/webhook/inapp сохранить.

Разделить два понятия:

- IntegrationConnection: один сервер/портал и бот, его реквизиты, внешняя идентичность и состояние.
- Channel: конкретный чат-получатель с connection_id. Одна connection может обслуживать несколько Channel.

Для старых каналов connection_id может быть пустым; миграция не должна требовать перенастройки Telegram и SMTP. Не делать перенос всех старых транспортов на новую модель условием выпуска новых.

Минимальные поля IntegrationConnection:

- id, provider, name, base_url, active;
- encrypted_credentials либо ссылка на защищённое хранилище;
- external_bot_id, public_config, credentials_version;
- setup_status, health_status, last_checked_at, last_event_at, last_error_code;
- server_revision/version, capabilities и дата их определения;
- generation для инвалидирования прежних привязок и действий при смене бота/сервера.

Канал содержит remote_chat_id строкой, безопасное отображаемое название, состояние проверки и привязки. Числовые Telegram-правила не применять к VK Teams/Mattermost/Bitrix dialogId.

Внешние ID всегда квалифицируются connection_id: одинаковые user_id или chat_id двух серверов не обозначают одного участника/получателя. По умолчанию не привязывать внешнего участника к веб-пользователю и не создавать ему административную сессию.

Для входящих событий нужна durable inbox с уникальностью connection_id + external_event_id. Для HTTP-действий, у которых нет отдельного ID события, использовать одноразовый идентификатор действия и сохранённый результат. Курсор polling хранить на connection и продвигать только после надёжного сохранения входящих данных. Данные входящего события хранить в минимальном объёме без токенов.

Существующий BotAction обобщить или выделить ChatAction: provider/connection/channel, occurrence, ожидаемая revision, инициатор, действие, выбранная дата, TTL и отметка исполнения. Существующий Telegram-сценарий не сломать.

## 3. API для frontend

Согласовать и закрепить в OpenAPI до разработки экранов. Все административные операции — admin_user.

Предлагаемые маршруты:

- GET /api/v1/integrations/providers — доступные адаптеры, поддерживаемые сценарии, поля настройки и ограничения совместимости.
- GET/POST /api/v1/integrations/connections — безопасный список и создание подключения.
- GET/PATCH /api/v1/integrations/connections/{id} — безопасная карточка и частичное изменение.
- POST /api/v1/integrations/connections/{id}/validate — проверка реквизитов и доступных возможностей без отправки счёта или регистрации нового бота.
- POST /api/v1/integrations/connections/{id}/setup — явная регистрация/настройка бота там, где это требуется. Сохранять частичный результат, чтобы повтор не плодил ботов/команды.
- GET /api/v1/integrations/connections/{id}/status — состояние, время проверки, приёма событий и безопасные причины ошибок.
- GET /api/v1/integrations/connections/{id}/destinations — только доступные этому боту чаты с пагинацией, если провайдер позволяет такую выборку; иначе отдельная проверка введённого ID.
- Существующие POST/PATCH /api/v1/channels расширить connection_id и параметрами чата; PATCH должен принимать active без полного повторения config.
- POST /api/v1/channels/{id}/bind — привязка и проверка выбранного чата. Для VK Teams может возвращать одноразовый код команды.
- POST /api/v1/channels/{id}/test с mode=interactive — тестовое сообщение и проверка обратного действия.
- GET /api/v1/integration-tests/{id} — результат конкретного теста.
- POST /api/v1/integrations/mattermost/{connection_id}/actions — публично достижимый callback, авторизуемый токеном действия, а не административной cookie.

validate/bind/setup/test могут возвращать 202 и job_id, если требуют сетевой работы. Не удерживать запрос интерфейса на протяжении long polling и не показывать success до завершения job. Test возвращает test_id и статусы sending, awaiting_click, passed, failed, expired.

Пример безопасной карточки подключения:

```json
{
  "id": "connection-id",
  "provider": "mattermost",
  "name": "Корпоративный Mattermost",
  "base_url": "https://chat.company.example",
  "active": true,
  "setup_status": "configured",
  "health_status": "not_checked",
  "has_credentials": true,
  "external_bot_id": null,
  "capabilities": {
    "native_actions": "unknown",
    "message_edit": "unknown",
    "file_upload": "unknown"
  },
  "last_checked_at": null,
  "last_error_code": null
}
```

capabilities подтверждаются для конкретного подключения. Наличие адаптера в коде не переводит неизвестную инсталляцию в verified.

## 4. Секреты и смена конфигурации

Реквизиты принимать отдельным write-only объектом credentials. В GET возвращать has_credentials/перечень настроенных секретов, без исходных значений. Для Битрикс24 весь inbound webhook URL — секрет, включая путь; не возвращать его как обычный config.url. Валидационные ошибки и ответы provider не должны содержать исходный запрос.

Предлагаемый вариант локального хранения: шифрование credentials проверенной библиотекой с отдельным INTEGRATIONS_ENCRYPTION_KEY из серверного окружения. Ключ не хранится рядом с зашифрованными записями и не возвращается клиенту. При отсутствии ключа новые секреты не принимать молча в plaintext. Подробности подключения не писать в логи, аудит, trace и сообщения об ошибках.

PATCH без credentials сохраняет секреты. Пустую строку не трактовать как новый токен. Явное удаление секрета разрешать отдельным действием с переводом подключения в состояние настройки. Переключатель active не передаёт и не перезаписывает токен.

Смена адреса сервера, внешнего бота или целевого чата требует повторной проверки, сброса соответствующего connected_at и инвалидирования старых действий/ограниченных ссылок. Ротация токена того же бота сохраняет чат только после успешной проверки внешнего bot_id. Не применять старую очередь к новому месту назначения без явного решения: pending jobs привязать к generation, устаревшие помечать skipped.

Сетевой клиент: HTTPS, проверка сертификата, конечные allowlisted origin, отсутствие автоматических redirects. Для on-premise разрешать конкретный доверенный host/сеть в серверной политике, а не включать доступ ко всем private IP. Собственный CA устанавливать в окружение; не добавлять кнопку «игнорировать TLS».

Для callback и ссылок нужен отдельный канонический PUBLIC_APP_URL. Не брать адрес из непроверенного Host-заголовка и не полагаться на первый элемент CORS allowlist как на публичный URL.

## 5. Общий транспорт и платёжные действия

Ввести небольшой интерфейс адаптера: validate_connection, validate_destination, send_invoice, update_invoice, acknowledge_action, send_receipt или receipt_link, normalize_event. Приём событий polling остаётся отдельным runner, использующим адаптер. Ветки send_delivery можно переносить постепенно; не переписывать всё приложение.

Общий сценарий:

1. Неоплаченный счёт содержит «Оплатить» и действие выбора фактической даты.
2. Нажатие только открывает подтверждение. Оно привязано к авторизованному внешнему участнику, подключению, чату, счёту и revision, действует 15 минут.
3. «Подтвердить» выполняет confirm_occurrence с demo=True и expected_revision. «Назад» не меняет счёт.
4. Использовать existing business timezone и проверки даты. Для выбора даты допустим календарь из кнопок или защищённое состояние ввода даты внутри чата; не требовать веб-перехода для самой оплаты.
5. После оплаты доступны чек, изменение даты и отмена отметки с отдельным подтверждением. При отмене самого счёта платёжные кнопки исчезают.

Обработчик проверяет: активное подключение/канал; тот же remote chat; выпуск счёта именно этому получателю; соответствие message reference; допустимого участника; срок и назначение action token; revision. Отказ без мутации при несовпадении. Токен — непрозрачный и непредсказуемый, в payload нет административных полномочий.

Для авторства хранить внешнюю идентичность provider:connection:user_id и отображаемое имя отдельно. Строка из внешнего события экранируется и не выдаётся за проверенный веб-логин.

Оплата, аудит, аннулирование/создание чека и постановка state/receipt jobs фиксируются транзакционно. Отправка в чат выполняется после commit. Ошибка внешнего сообщения не отменяет уже совершённую демооплату и не создаёт второй чек при повторе события.

Сообщения одной оплаты могут быть отправлены нескольким получателям. Изменение через один канал должно обновить остальные сообщения этого счёта. Хранить внешние message refs и синхронизированную revision; обработка устаревшего state job не должна окончательно перезаписать новый статус. При необходимости сериализовать обновления одного счёта/канала и повторно сверять revision.

Существующие ссылки email остаются совместимыми. Для чека в новом чате сделать отдельное ограниченное право receipt.read: ссылка на один действующий чек, TTL, отсутствие доступа к спискам и админке. Не расширять email-код простой отменой kind-проверки: там actor зависит от config.email. Нативный файл — дополнительный транспорт чека; ошибки загрузки не отменяют оплату.

## 6. VK Teams

- base_url и токен задаются на connection; проверка через self/get.
- Чат добавляется вручную в VK Teams, затем связывается кодом из приложения. Код одноразовый, хранится безопасно, TTL 10 минут. Подтверждать полномочия привязывающего через getAdmins либо требовать явную проверку выбранного чата администратором приложения.
- Реализовать sendText, editText, sendFile, answerCallbackQuery и events/get по закреплённым официальным схемам.
- Сохранять lastEventId после durable inbox. На connection один polling consumer с lease; несколько чатов не создают несколько конкурирующих опросов одного бота.
- Callback нормализовать из явного user/chat/message context. Не смешивать старую структуру SDK и текущую Swagger-схему без версионированных fixtures.
- Отвечать на callback и при ошибке/просроченном действии. Токен в query string и чувствительные callback-данные не попадают в access logs.
- Удаление бота из чата или потерю прав показывать как chat_unavailable/insufficient_permissions, не как успешную отправку.

## 7. Mattermost

- Выбранный режим: bot account с access token; incoming webhook не заменяет этот режим.
- Проверить /api/v4/users/me и доступ к указанному каналу; убедиться, что реквизиты принадлежат ожидаемому боту. Не повышать ему роль до system admin ради удобства.
- POST /api/v4/posts возвращает post id, который сохраняется. Для частичной синхронизации использовать PUT /api/v4/posts/{id}/patch, сохраняя нужные props.
- Основной рендерер — Blocks при подтверждённой поддержке. Legacy attachment actions — явно выбранный совместимый профиль. В обоих случаях дополнительно сохранять обычный текст счёта.
- Callback проверяет секретный per-action context token, connection/channel/post/участника и revision. У стандартного interactive callback нет основания автоматически считать любой HTTP-запрос подписанным Mattermost. Не изобретать обязательный X-Signature, которого нет в выбранном контракте.
- Callback должен быть доступен именно серверу Mattermost. Private маршрутизация допускается по явной политике окружения. Отдельный WebSocket не нужен.
- Использовать персональное сообщение-подтверждение из ответа действия, если профиль поддерживает его. Не менять общую карточку счёта на личную форму участника. При необходимости отдельное сообщение с user-bound токеном.
- Если токен/версия/права не позволяют интерактивность или редактирование, подключение не считается полностью готовым. При политическом запрете редактирования возможен явный режим «новое сообщение со статусом», а не скрытый неуспех обновления.

## 8. Битрикс24, отдельный этап

- Режим для первого выпуска: imbot.v2, входящий REST webhook со scope imbot, eventMode=fetch. Пользовательские im.message.* и CRM-интеграция не входят в этот транспорт.
- При validate проверить доступность imbot.v2.Revision.get и требуемых методов/прав. При несовместимости вернуть unsupported_server, не переключаться молча на старый API.
- По отдельному setup создать или подключить бота, сохранить botId и защищённый botToken. Генерировать botToken подходящей длины — не более 40 символов. Повтор setup использует существующие botId и зарегистрированные command IDs.
- Зарегистрировать локальную команду invoice_action, hidden при необходимости. Все кнопки действий используют эту команду и непрозрачный COMMAND_PARAMS, а не произвольные команды управления системой.
- Получать ONIMBOTV2COMMANDADD через imbot.v2.Event.get, сохранять события и nextOffset надёжно. При hasMore читать следующую страницу, при пустой очереди ждать с backoff.
- Сверять botId, chat.dialogId, user.id, команду, токен и разрешение на конкретный счёт. Ручной вызов команды без валидного действия не оплачивает счёт.
- Отправлять/обновлять через imbot.v2.Chat.Message.send/update; клавиатуры явно адресовать нужному BOT_ID. Нажатие ACTION:SEND не считать надёжной оплатой.
- Webhook eventMode и OAuth можно добавить отдельно. Если реализуется webhook mode, обрабатывать form-urlencoded и проверять верхнеуровневый auth.application_token; не доверять адресам и токенам из произвольного тела запроса.
- Учесть отсутствие REST на неподходящем плане и отсутствие метода на старой коробке. Возвращать понятную причину настройки вместо бесконечного retry.

## 9. Фоновые процессы и надёжность

Сохранить существующую очередь Delivery и уникальность occurrence/channel/event. Для polling нужен отдельный app.integration_events runner или аналогичный сервис в Compose, не блокирующий app.worker длительным запросом. Пауза на сеть одного провайдера не останавливает остальные отправки.

Поведение ошибок:

- invalid credentials/permissions: остановить бесполезные повторы этого подключения, сохранить reason code; другие подключения работают.
- Rate limit: учитывать Retry-After, если он есть, либо provider-specific backoff с jitter. Для Битрикс24 различать rate limit и resource limit по error code.
- HTTP 200 недостаточно: разбирать ok и provider error object.
- Timeout после возможного принятия сообщения: uncertain, без слепой повторной отправки. Локальный Delivery ID не означает внешнюю exactly-once гарантию.
- Повтор полученного события: вернуть прежний результат без повторной оплаты или чека.
- Ошибка синхронизации сообщения/выдачи чека: отдельная наблюдаемая job; бизнес-статус оплаты сохраняется.

Тест подключения не использует случайный реальный счёт. Сейчас /channels/{id}/test берёт latest_active_occurrence; заменить для новых интеграций тестовой сущностью/задачей с нейтральным текстом и безопасной noop-кнопкой. Нажатие доказывает обратную связь и никогда не вызывает confirm_occurrence.

## 10. Минимальные критерии приёмки

Автоматически, без внешних реквизитов:

- Точные method/path/auth/payload и форматы клавиатур по fixtures каждого поддерживаемого профиля.
- VK: ok=false при HTTP 200, callbacks разных форм, курсор, рестарт, один poller на бота.
- Mattermost: callback с валидным и поддельным context, неправильным post/channel/user, Blocks/legacy, запрет редактирования, 401/403/429.
- Bitrix: setup без дублей, отсутствие revision/scopes, командный callback через fetch, корректное подтверждение nextOffset после сохранения, ограничения запросов.
- Два участника одновременно подтверждают один счёт: одна оплата и один действующий чек. Второй получает понятный актуальный статус.
- Истёкший токен, смена чата/бота, отключение подключения и чужой чат не меняют счёт.
- Дата/отмена/чеки и история работают одинаково для one_time и recurring.
- После оплаты через один канал другие сообщения обновляются; сбой одного провайдера не блокирует остальные.
- Секреты не присутствуют в GET, ошибках, логах, аудите и frontend fixtures.
- Миграция сохраняет Telegram/email/webhook/inapp и существующие данные.

Отдельный live smoke после появления инсталляции: проверка бота, добавление в тестовый чат, отправка теста, нажатие, создание демосчёта, оплата/дата/отмена/чек, перезапуск. Без этого результат обозначать «реализовано и проверено по контрактам; требуется проверка на инсталляции».
