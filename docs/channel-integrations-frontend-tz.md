# ТЗ frontend: подключения VK Teams, Mattermost и Битрикс24

Исходный сценарий и официальные ссылки: [общий план](./channel-integrations-plan.md). API и безопасность: [ТЗ backend](./channel-integrations-backend-tz.md). Предлагаемые маршруты API ещё не реализованы; согласовать их до разработки форм.

## 1. Результат для пользователя

Администратор выбирает платформу, вводит адрес и реквизиты, проверяет бота, связывает нужный чат и проверяет кнопку. После этого он выбирает канал в аудитории счёта обычным способом. Участник чата подтверждает демонстрационную оплату внутри мессенджера без веб-аккаунта.

Обязательные платформы — VK Teams и Mattermost. Битрикс24 показывать как поддерживаемый только после реализации его адаптера. До этого допустима честная отметка «Планируется» без работающей кнопки подключения.

Форма без реквизитов может быть сохранена как черновик. Не показывать фиктивное «Подключено» и не подставлять демонстрационные токены. Подсказки и инструкции доступны до подключения.

## 2. Организация интерфейса

Расширить существующую страницу «Подключения», сохранив текущие Telegram, Email и Webhook.

Сущности в интерфейсе:

- Подключение: платформа, сервер и бот. Реквизиты вводятся один раз.
- Получатель: чат внутри выбранного подключения. Можно добавить несколько чатов одного сервера.

Не создавать несколько копий секретов для каждого чата. В карточке получателя показывать название чата, платформу и безопасное имя сервера, а не secret URL.

Мастер подключения:

1. «Сервис» — выбор платформы и краткое описание «Счета, напоминания и подтверждение оплаты в чате».
2. «Бот и доступ» — форма для выбранного сервиса и раскрываемая инструкция получения реквизитов.
3. «Проверка» — результат проверки API/бота и, для Битрикс24, отдельное явное создание/подключение бота.
4. «Чат» — выбор доступного чата либо ввод его ID с серверной проверкой; для VK Teams также код привязки.
5. «Тест» — отправка нейтрального сообщения, затем ожидание нажатия безопасной тестовой кнопки.

Это не обязано быть пятью отдельными страницами: компактный диалог с текущим шагом и сохранением черновика достаточен. «Назад» не теряет несекретные значения. Не сохранять реквизиты в localStorage/sessionStorage, query-параметрах и аналитике.

## 3. Поля провайдеров

### VK Teams

- Название подключения.
- URL Bot API. По умолчанию можно предложить текущий облачный URL из backend-каталога; для корпоративного сервера поле изменяемое.
- Токен бота — password, write-only.
- После проверки — безопасное имя/ID бота.
- Название получателя и привязанный chat_id. Код команды генерирует backend, TTL отображается рядом.

ID хранить и передавать строкой. Не применять Telegram-валидацию «только цифры». Не обещать Telegram-подобный выбор группы по ссылке, пока поставщик явно не поддерживает такой путь.

### Mattermost

- Название подключения.
- URL сервера, например https://chat.company.example.
- Access token bot account — password, write-only; явно отличать от Token ID.
- Чат-получатель: разрешённый боту список либо channel ID с проверкой.
- В дополнительных параметрах — профиль карточек, если требуется совместимость: «Современные карточки» и «Совместимый формат». Техническое соответствие Blocks/legacy можно объяснить в справке.

Не просить incoming webhook URL в основном сценарии: здесь используется бот с REST. Проверка не должна требовать администраторский токен Mattermost. Если возможности сервера неизвестны, финальный тест кнопки остаётся обязательным шагом готовности; принятие JSON сервером не доказывает отображение кнопки клиентом.

### Битрикс24

- Название подключения.
- URL входящего webhook — секретное поле. Backend разбирает его и возвращает только безопасное имя портала. Можно отдельно показывать адрес портала для сверки.
- «Проверить доступ» — revision, доступность imbot и права владельца webhook.
- Режим «Создать бота» или «Подключить существующего».
- Для нового бота — отображаемое имя; botToken генерирует и хранит backend, повторного ручного ввода не требовать.
- Для существующего — botId и botToken, если используется выбранная webhook-авторизация.
- Целевой dialogId либо доступный список чатов. Предусмотреть групповой chatXXX, не путать с числовым внутренним ID.

Кнопка «Создать бота» — отдельное явное действие администратора. «Проверить доступ» сама по себе не создаёт сущности на чужом портале. Известный botId сохраняется при частично неуспешном setup, чтобы повтор не создавал дубликаты.

## 4. Готовые тексты инструкций для фронтенда

Тексты ниже предназначены для секций «Как подключить». Встроить непосредственно в страницу или локальную справку, доступную без реквизитов. Ссылки ведут на официальную документацию; названия меню могут отличаться в корпоративной инсталляции.

### Как подключить VK Teams

1. Откройте VK Teams своей организации и найдите Метабота. Создайте бота командой /newbot и сохраните выданный токен.
2. В Invoice Keeper выберите VK Teams. Укажите URL Bot API вашего окружения и вставьте токен. Для корпоративного сервера адрес уточните у администратора VK Teams.
3. Нажмите «Проверить бота». Приложение покажет найденного бота; убедитесь, что это нужная учётная запись.
4. Добавьте бота в нужный групповой чат и разрешите необходимые действия с сообщениями. Для отправки файлов дополнительно нужны соответствующие права.
5. Получите в Invoice Keeper код привязки и отправьте указанную команду в целевой чат. Привязку подтверждает администратор чата либо администратор Invoice Keeper по предусмотренному сценарию проверки.
6. Нажмите «Отправить тест», затем «Проверить кнопку» в сообщении VK Teams. Тест не изменяет реальные счета.
7. Добавьте получателя в группу рассылки или выберите его при создании нового счёта.

Подсказка: «Бот не подключается? Проверьте URL именно Bot API, токен и доступ сервера Invoice Keeper к корпоративному окружению. Бот, созданный в другом окружении, может не работать с этим адресом».

Ссылки: [Bot API](https://teams.vk.com/botapi/), [инструкция официального SDK](https://github.com/mail-ru-im/bot-python/blob/master/README.md).

### Как подключить Mattermost

1. Попросите администратора Mattermost разрешить создание bot accounts, если эта функция недоступна.
2. В разделе Integrations → Bot Accounts создайте отдельного бота Invoice Keeper. Сохраните показанный access token; Token ID для подключения не подходит.
3. Добавьте бота в нужную команду и канал. Для закрытого канала бот должен иметь соответствующий доступ. Не выдавайте ему системного администратора только ради отправки счетов.
4. В Invoice Keeper укажите URL сервера и access token, нажмите «Проверить бота».
5. Выберите канал либо вставьте его channel ID и проверьте доступ.
6. Убедитесь, что сервер Mattermost может обратиться к адресу обработки кнопок Invoice Keeper. Для изолированной сети это настраивает администратор сервера.
7. Отправьте тест и нажмите тестовую кнопку в Mattermost. Если кнопка не отображается, проверьте поддерживаемый формат карточек и политику сервера.
8. После успешного теста включите получателя в рассылку.

Подсказка: «Сообщение пришло, но кнопка не отвечает? Проверьте доступ Mattermost к обработчику Invoice Keeper и поддержку интерактивных сообщений. Повторный ввод токена не исправляет сетевую недоступность обработчика».

Ссылки: [Bot accounts](https://docs.mattermost.com/developers/integrate/reference/bot-accounts), [интерактивные сообщения](https://docs.mattermost.com/developer/interactive-messages), [формат карточек](https://docs.mattermost.com/developers/integrate/reference/mm-blocks).

### Как подключить Битрикс24

1. Убедитесь, что на вашем портале доступны REST API, входящие webhook и нужные методы Chatbots 2.0. Устаревшая коробочная версия или тариф могут ограничивать подключение.
2. В разделе ресурсов для разработчиков создайте входящий webhook с разрешением imbot. Копируйте полный URL только в секретное поле Invoice Keeper.
3. Нажмите «Проверить доступ». Приложение проверит доступность API; при несовместимости покажет причину.
4. Выберите «Создать бота» и задайте его имя. Invoice Keeper зарегистрирует бота и команды. Если бот уже создан этим подключением, используйте его повторно.
5. Добавьте бота в чат, куда нужно отправлять счета, и укажите или выберите этот чат в Invoice Keeper.
6. Отправьте тест и нажмите тестовую кнопку в Битрикс24. Для выбранного режима события забирает Invoice Keeper; отдельный публичный обработчик Битрикс24 не требуется.
7. После проверки включите получателя в рассылку.

Подсказка: «Входящий webhook разрешает Invoice Keeper обращаться к API Битрикс24. События нажатий получает бот; одного URL для отправки сообщений недостаточно без настройки бота и команд».

Ссылки: [настройка webhook](https://helpdesk.bitrix24.com/open/21133100/), [Chatbots 2.0: начало работы](https://apidocs.bitrix24.com/api-reference/chat-bots/chat-bots-v2/quick-start.html).

## 5. Состояния и обратная связь

Разделить независимые признаки:

- канал включён/отключён;
- реквизиты отсутствуют/сохранены/ошибочны;
- бот настроен/нужна настройка;
- чат привязан/не привязан/недоступен;
- исходящая отправка проверена/не проверена;
- кнопка проверена/ожидается нажатие/ошибка;
- приём событий работает/давно не проверялся.

«Включён» не означает «подключён», а «API доступен» не означает «оплата кнопкой работает». На первом экране не обязательно показывать все технические признаки: достаточно основного статуса и следующего действия, подробности — раскрываемые.

У теста отдельная последовательность: «Поставлен в очередь» → «Отправлен» → «Ожидаем нажатие кнопки в чате» → «Кнопка работает». Сетевой таймаут — «Результат отправки неизвестен, проверьте чат». По истечении срока теста — «Тест истёк», без изменения финансовых данных.

Получать статус test_id через ограниченный polling с остановкой на terminal state и при уходе со страницы. Не запускать бесконечный опрос из каждого компонента списка.

Для ошибок использовать коды backend и понятные тексты:

- credentials_invalid: «Проверьте реквизиты подключения»;
- insufficient_permissions: «Боту не хватает прав для этого действия»;
- unsupported_server: «Эта версия или настройка сервера не поддерживает выбранный сценарий»;
- chat_unavailable: «Чат недоступен этому боту»;
- callback_unreachable: «Сервер мессенджера не может связаться с Invoice Keeper»;
- rate_limited: «Сервис временно ограничил запросы; повтор запланирован»;
- delivery_uncertain: «Не удалось подтвердить отправку. Сначала проверьте чат».

Не показывать raw provider errors, секретные URL, токены и стеки. Подробности должны помогать исправить подключение, а не раскрывать внутреннее устройство приложения.

## 6. Секреты и редактирование

После сохранения показывать «Реквизиты сохранены» и действие «Заменить», не загружать секрет назад с сервера. Не вставлять фиктивные звёздочки в значение поля и не отправлять их как токен.

Изменение названия и active не требует повторного ввода реквизитов. PATCH отправляет только изменённые поля; существующее toggle с полным channel.config переработать совместно с backend.

При смене сервера, бота или чата показать, что нужна повторная проверка. Не сохранять старый статус теста для нового места назначения. При успешной ротации токена того же бота можно сохранить привязку только согласно ответу backend.

Поля password не логировать, не включать в ссылки, формы обратной связи и frontend fixtures. Для Битрикс24 секретен весь webhook URL, а не только последний фрагмент.

## 7. Остальные экраны

### Группы и выставление счёта

Добавить новые провайдеры в единый справочник ChannelKind/channelLabels и icon mapping. Группы рассылки продолжают работать через channel_ids без отдельных массивов для каждой платформы.

В preview аудитории показывать включённые каналы и предупреждать, если подключение не настроено или чат недоступен. Не терять выбранного получателя молча. Сохранить понятное различие выбора аудитории и фактической готовности отправки.

Правила одинаковы для one_time и recurring. Обязательная периодичность не появляется у разового счёта из-за нового канала.

### Журнал уведомлений

Добавить новые виды каналов и фильтры, безопасное имя сервера/чата, понятные причины ошибок, ссылку на карточку подключения. sent подписывать «Отправлено», без обещания прочтения.

Отличать ошибку исходной отправки, ошибку обновления сообщения после оплаты и ошибку выдачи чека. Если оплата уже сохранена, сбой мессенджера не должен показывать пользователю, что счёт снова неоплачен.

### Карточка счёта

Отображать оплату и автора из внешнего канала понятным текстом, например «Подтверждено в Mattermost». Имя из чата не выдавать за проверенный логин веб-пользователя.

Для администратора допустима сводка синхронизации по каналам. Обычному пользователю не показывать секреты подключения и техническую диагностику рассылки.

Не создавать три новых веб-страницы оплаты по провайдерам. Основной сценарий исполняется в чатах; существующий /pay/:token для email сохраняется. Ссылка за чеком имеет только право чтения и может вести непосредственно на безопасную выдачу файла backend.

## 8. Структура frontend

Обновить entities/channel и её публичный API: discriminated ChannelKind, типы Connection/Capabilities/TestResult, общие подписи и вычисление состояния. Предпочтительно вынести API подключения в этот слайс.

Мастер и провайдерные формы могут оставаться локальными компонентами pages/settings/ui, без переноса доменного кода в shared. Если возникнет действительно переиспользуемый сценарий подключения, выделить feature с разрешёнными зависимостями FSD. Не создавать слой features только ради одного большого компонента.

Изменить pages/groups, pages/create-payment, pages/notifications и при необходимости payment-detail. Обновить shared/ui/AppIcon. Все импорты между слайсами — через public API.

Пользовательские инструкции хранить рядом с провайдерными формами или в локальном справочнике контента; ссылки на документацию собирать в одном месте, чтобы их можно было обновить.

## 9. Проверка готовности

- Создание/редактирование черновика без реальных реквизитов; отсутствие ложного connected.
- Три формы показывают только нужные поля; смена провайдера очищает секретные значения прошлого провайдера.
- Проверка реквизитов, частично выполненный setup, выбор чата, повторная проверка и test_id проходят с mock API.
- Toggle и переименование не стирают секреты.
- Инструкции доступны до настройки и содержат получение реквизитов, права, добавление бота, тест и типичные ошибки.
- Успешная исходящая отправка не завершает проверку кнопки до callback.
- Ошибки прав/версии/сети/лимитов/uncertain различимы.
- Обычный пользователь не открывает административные подключения через меню и прямой URL; запрет API проверяет backend.
- Новые провайдеры видны в группах, preview аудитории, фильтрах и журнале.
- Мобильная ширина 360 px, клавиатура, фокус диалога, доступные названия кнопок; длинные URL и ошибки не ломают форму.
- npm run check и npm run build; добавить осмысленные проверки переходов мастера и сохранения секретов, а не только тесты строк справочника.

Финальный smoke с настоящим мессенджером выполняется отдельно после появления окружения. До него инструкция и mock не считаются доказательством реальной доставки.
