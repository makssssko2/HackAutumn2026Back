# B2B API входящих счетов — план бэкенда

Дата: 24.10.2026. Статус: проект решения, реализация ещё не начата.

Подтверждённый сценарий: контрагент выставляет нашей компании входящий счёт со своими реквизитами, суммой, сроком и документом. Мы проверяем счёт, принимаем либо отклоняем и отдельно учитываем оплату.

## 1. Результат первой версии

Партнёр получает API-ключ, создаёт черновик счёта, прикладывает PDF и отправляет на проверку. Наш сотрудник видит счёт во внутреннем реестре, принимает или отклоняет с причиной. Партнёр получает актуальный статус через API. После фактической оплаты уполномоченный сотрудник фиксирует её во внутреннем API.

«Открытое API» означает документированный интерфейс для внешних компаний с авторизацией. Выдача доступа — через администратора, без самостоятельной регистрации в MVP.

Границы MVP:

- Одна наша компания-покупатель; отдельная запись организации, чтобы затем поддержать несколько юрлиц без смены контракта.
- Разовые входящие счета, полная оплата одной суммой, валюта RUB.
- Проверка и принятие счёта обязательны. Приём API-запроса не означает согласование или оплату.
- PDF счёта обязателен перед отправкой на проверку; дополнительные PDF, PNG и JPEG допустимы.
- Отдельный реестр входящих счетов и внутренние endpoints для работы с ним. Интерфейс фронтенда — отдельная задача; необходимые ему API входят в план.
- Нет банковских переводов, автоматической проверки оплаты, частичных оплат, ЭДО, юридической подписи, OCR, регулярных счетов и интеграции с бухгалтерией.
- Нет автоматического включения в существующий бюджет: это последующий этап после определения правила учёта. Отдельный реестр предотвращает двойной учёт.

## 2. Что уже есть в проекте

Ниже — факты по текущему коду, а не реализованные возможности B2B.

- FastAPI, SQLAlchemy, Alembic; в Compose используется PostgreSQL.
- `app/core/security.py`: пользователи авторизуются cookie-сессией, роли `admin` и `user`. Отдельного контрагента и машинной авторизации нет.
- `app/api/one_time_payments.py`: создание разового платежа доступно администратору.
- `app/models.py`: счета представлены `RecurringPayment` и `Occurrence`; реквизитов поставщика, покупателя и согласования нет.
- `app/domain/services.py`: отметку оплаты использует существующий сценарий, в том числе демонстрационный. Это не подтверждение банковского перевода.
- `app/api/occurrences.py`, `app/payment_access.py`: менять отметку оплаты могут текущие пользователи и получатели по специальной ссылке в рамках существующих правил.
- `app/notifications.py`: задания `Delivery` хранятся в БД, отдельный worker отправляет уведомления. Выбор получателей без групп может включать все активные каналы.
- `app/api/attachments.py`: есть загрузка файлов с ограничением размера и проверкой сигнатур; доступ привязан к текущим счетам и пользовательским сессиям.
- `app/main.py`: публичные Swagger/OpenAPI отключены; действуют общие CORS и проверки Origin.

Поэтому нельзя просто открыть партнёрам существующий endpoint создания платежа или выдать им административный логин.

## 3. Архитектурное решение

Добавить отдельный домен `incoming invoices` в существующий бэкенд и БД. Использовать общие инфраструктурные компоненты: подключения к БД, миграции, аудит, логирование, worker. Существующие модели счетов и их публичные платёжные ссылки в MVP не связывать с входящими счетами.

Поток:

```text
Система контрагента
  → /api/b2b/v1 + API-ключ + Idempotency-Key
  → проверка партнёра, разрешений, владельца и данных
  → транзакция: счёт/смена статуса + история + outbox-событие
  → ответ с идентификатором и статусом

Worker → внутреннее уведомление о новом входящем счёте
Наш сотрудник → внутреннее API → принять / отклонить / учесть оплату
Контрагент → GET своего счёта → актуальные статусы
```

В MVP отдельный брокер не нужен. Outbox — таблица событий в той же БД, записываемая в одной транзакции с изменением счёта. Доставка уведомления не должна блокировать создание счёта. Ошибка уведомления не откатывает уже принятый счёт.

Текущая `Delivery` содержит обязательный `occurrence_id`, поэтому использовать её напрямую для нового домена нельзя. Для входящих счетов нужны отдельные события и задания доставки. Существующие уведомления продолжают работать по прежним правилам.

## 4. Модель данных

### Организации и доступ

- `BuyerOrganization`: наша компания, внутренний ID, наименование, ИНН, КПП, активность. API публикует только разрешённые партнёру данные покупателя.
- `BusinessPartner`: контрагент, проверенные наименование, ИНН, КПП, контакты, статус `active/blocked`, временные метки.
- `PartnerBuyerAccess`: разрешённые пары «партнёр — наша организация»; уникальность пары.
- `PartnerBankAccount`: реквизиты получателя, принадлежащие партнёру, с признаком проверки и активностью. В MVP их заводит/подтверждает администратор. Партнёр выбирает ID счёта и не подменяет банковские реквизиты произвольным JSON.
- `PartnerApiKey`: партнёр, окружение `test/live`, публичный префикс, хеш секрета, разрешения, срок действия, отзыв, дата последнего использования. Несколько ключей обеспечивают ротацию.

### Счёт и документы

- `IncomingInvoice`: ID, партнёр, покупатель, окружение, `external_id`, номер и дата счёта, срок оплаты, назначение, сумма, валюта, ссылка на банковский счёт партнёра, `review_status`, `payment_status`, `revision`, даты создания/изменения/отправки/решения.
- При отправке сохранять неизменяемый снимок реквизитов поставщика, покупателя и банковского счёта. Последующая правка справочника не меняет уже выставленный счёт.
- Сумму хранить как `Numeric(14, 2)`/`Decimal`, в JSON передавать строкой. В MVP — положительная итоговая сумма в RUB. Налоговые расчёты и табличную часть не выводить автоматически из PDF; добавить отдельным расширением контракта при необходимости.
- `IncomingInvoiceDocument`: счёт, тип `invoice/supporting`, оригинальное имя, серверное имя хранения, MIME, размер, SHA-256, состояние загрузки/проверки. У документа нет публичного URL.
- `IncomingInvoiceHistory`: действие, прежнее и новое состояние, актор, причина, дата, `request_id`. История добавляется, а не перезаписывается.
- `IncomingInvoicePayment`: счёт, сумма и валюта, дата фактической оплаты, номер/ссылка подтверждения, кто и когда внёс запись, сведения об отмене ошибочной записи. Только одна действующая запись полной оплаты на счёт; отменённые записи сохраняются. `payment_status` изменяется вместе с записью оплаты в одной транзакции.

### Надёжность

- `PartnerIdempotencyRecord`: партнёр, окружение, ключ, отпечаток запроса, HTTP-код и сохранённый ответ, время создания.
- `IncomingInvoiceOutbox`: ID события, ID счёта, версия, тип, минимальные данные события, время создания и состояние обработки.
- `IncomingInvoiceNotification`: событие, явно выбранный внутренний получатель, попытки, следующий запуск, состояние доставки, ошибка, срок захвата задания.

Ограничения БД и индексы:

- Постоянная уникальность `(partner_id, environment, buyer_id, external_id)`.
- Уникальность `(partner_id, environment, idempotency_key)`.
- Уникальность события по `(invoice_id, revision, event_type)` и уведомления по `(event_id, destination_id)`.
- Проверки положительной суммы, допустимых статусов и согласованности статуса оплаты.
- Индексы списков по партнёру/окружению/дате/ID и внутренней очереди по покупателю/статусу/дате/ID.
- Покупатель, банковский счёт и партнёр должны принадлежать разрешённой связке; это проверяется в сервисе, а где возможно — составными внешними ключами.

## 5. Авторизация и изоляция

Использовать `Authorization: Bearer <api_key>` для серверных интеграций. Секрет генерировать криптографически случайным, показывать один раз и хранить только его хеш. Публичный префикс позволяет находить запись ключа без хранения секрета. Не помещать ключи в URL, аудит или логи.

Разрешения MVP: `invoices:read`, `invoices:write`, `documents:read`, `documents:write`. Выдача/отзыв ключей и блокировка партнёра — только через внутренний admin API. Проверять отзыв, срок, окружение и блокировку на каждом запросе.

`partner_id` и окружение определяются по ключу, а не принимаются от вызывающей стороны. Все операции со счётом, документом, историей и списком включают фильтр владельца. Чужой ID возвращает `404`. Связи в теле запроса также проверяются на принадлежность. Партнёру не доступны пользователи, каналы рассылки, общие бюджеты и чужие документы.

Внутренние согласование и учёт оплаты в MVP доступны только `admin`. Роль бухгалтерии можно выделить позднее. Партнёр не может выставить себе статус `approved` или `paid`.

Тестовые данные изолированы по окружению на всех запросах и задачах. Ключ `test` не создаёт рабочую задолженность и не отправляет сообщения рабочим получателям.

## 6. Жизненный цикл

Согласование и оплата — два отдельных поля.

`review_status`:

- `draft`: партнёр редактирует поля и документы.
- `submitted`: отправлено нам; реквизиты и финансовые поля зафиксированы.
- `approved`: принято нашей компанией к дальнейшей оплате.
- `rejected`: отклонено с обязательной причиной.
- `cancelled`: отозвано/отменено; история сохранена.

`payment_status`: `unpaid` или `paid`. Просрочка вычисляется по сроку для принятого неоплаченного счёта и не хранится отдельным изменяемым статусом.

Переходы:

- Партнёр: `draft → submitted`, `draft/submitted → cancelled`.
- Администратор: `submitted → approved/rejected`; `approved + unpaid → cancelled` с причиной.
- Отметка оплаты: только для `approved + unpaid`, только внутренним администратором, с датой, суммой и ссылкой/номером подтверждающего документа.
- Исправление ошибочной отметки оплаты: отдельная внутренняя операция с обязательной причиной, новой ревизией и полной историей; прямое редактирование записей не допускается.
- Оплаченный счёт нельзя отозвать или отменить. Изменение суммы после отправки не допускается: создаётся новый счёт с новым `external_id` и ссылкой `supersedes_invoice_id` на предыдущий свой счёт. Отклонённый счёт остаётся неизменным.

У каждого изменения — проверка `expected_revision` и условное обновление строки. Параллельные принятие, отзыв и оплата должны разрешаться атомарно; проигравший запрос получает `409 revision_conflict`, перечитывает состояние и принимает новое решение.

MVP фиксирует сведения о фактической оплате вручную и не проверяет их в банке. Не использовать существующие демонстрационные чеки как доказательство оплаты.

## 7. Контракт внешнего API

Базовый путь: `/api/b2b/v1`. Только HTTPS. Параметры и ответы отделены от внутренних Pydantic-схем; неизвестные поля отклоняются.

- `GET /me`: партнёр, окружение, разрешения, доступные покупатели и проверенные банковские счета.
- `POST /invoices`: создать черновик, вернуть `201`, `Location`, ID и `revision`.
- `GET /invoices`: только свои счета; фильтры по статусам, датам и `external_id`; обязательная ограниченная пагинация.
- `GET /invoices/{id}`: свои реквизиты, сумма, статусы, причина решения и список документов без внутренних заметок.
- `PATCH /invoices/{id}`: изменить только черновик, передав `expected_revision`.
- `POST /invoices/{id}/documents`: загрузить файл в свой черновик с проверкой ревизии; увеличить ревизию счёта.
- `GET /invoices/{id}/documents/{document_id}/download`: скачать свой документ после проверки доступа и готовности файла.
- `DELETE /invoices/{id}/documents/{document_id}`: убрать документ только из черновика с проверкой ревизии.
- `POST /invoices/{id}/submit`: проверить обязательные реквизиты и готовый PDF, зафиксировать снимки, перейти в `submitted`.
- `POST /invoices/{id}/cancel`: отозвать допустимый счёт с причиной и ревизией.
- `GET /invoices/{id}/history`: только внешние события и разрешённые причины решений.

Пример создания:

```json
{
  "external_id": "erp-invoice-2026-1042",
  "buyer_id": "<ID нашей организации из GET /me>",
  "bank_account_id": "<ID проверенного счёта партнёра>",
  "number": "1042",
  "issued_at": "2026-10-24",
  "due_date": "2026-11-05",
  "title": "Услуги за октябрь 2026",
  "description": "По договору № 15",
  "amount": "150000.00",
  "currency": "RUB"
}
```

Последовательность клиента: создать → загрузить PDF → отправить на проверку → опрашивать свой статус. Создание и отправка — разные операции, чтобы неполный счёт не попадал в обработку.

Для списков — единый ответ `items`, `next_cursor`; сортировка по неизменяемым `(created_at, id)`, размер страницы по умолчанию 50, максимум 100. Курсор привязать к фильтрам и владельцу. Не наследовать внутренний режим возврата неограниченного массива.

Ошибки имеют единый формат `error.code`, `error.message`, `error.fields`, `request_id`. Основные коды: `401` — ключ, `403` — разрешение/блокировка, `404` — недоступный ресурс, `409` — конфликт версии/дубль/недопустимый переход, `413` — размер, `415` — формат файла, `422` — данные, `429` — лимит с `Retry-After`.

## 8. Повторные запросы и транзакции

Для JSON-команд `POST`/`PATCH`, включая создание, отправку, отзыв и внутренние решения, обязателен `Idempotency-Key`. Уникальность ключа — в рамках партнёра и окружения, а не конкретного API-ключа: ротация ключа не нарушает защиту от дублей.

- Отпечаток включает метод, нормализованный путь и нормализованное тело. Один ключ с другим запросом возвращает `409 idempotency_conflict`.
- Одинаковый запрос возвращает сохранённые HTTP-код и ответ после проверки действующей авторизации. Даже при изменении счёта возвращается результат исходной команды; актуальное состояние доступно через GET.
- Резервирование ключа, доменное изменение, история, событие и сохранённый успешный ответ коммитятся вместе. Если процесс упал до commit — изменений нет, повтор разрешён. Если после commit — повтор возвращает сохранённый результат.
- Конкурентные одинаковые запросы сериализуются ограничением БД; ожидание ограничено, при занятой операции возможен документированный `409 request_in_progress` с указанием повторить тот же запрос.
- Предлагаемый срок хранения полного ответа — 7 дней. Уникальность `external_id` сохраняется всё время: после очистки idempotency-записи повторное создание не порождает второй счёт, а возвращает `409 duplicate_external_id` с ID своего существующего счёта.
- Для загрузки файлов отдельная идемпотентность по ключу и отпечатку содержимого; для повторного удаления — документированный успешный ответ без повторного эффекта.

Нельзя гарантировать доставку SMTP «ровно один раз»: outbox обеспечивает сохранность намерения отправить, но не устраняет неопределённый исход внешней отправки. Состояние счёта остаётся источником истины.

## 9. Внутреннее API и уведомления

Внутренние пути под `/api/v1/incoming-invoices` используют пользовательские сессии и отдельную проверку административных полномочий:

- Список, карточка, история и скачивание документа.
- `POST /{id}/approve`, `POST /{id}/reject`, `POST /{id}/cancel`.
- `POST /{id}/record-payment`, `POST /{id}/reverse-payment`.
- Отдельный admin API организаций, контрагентов, банковских реквизитов, выдачи/отзыва ключей и доступа к покупателю. Список ключей возвращает только метаданные.

О решении и оплате создаются события `incoming_invoice.submitted/approved/rejected/cancelled/payment_recorded/payment_reversed`. Внешний статус доступен независимо от доставки уведомления.

В MVP обязательное уведомление — сотрудникам о поступлении счёта. Получатели настраиваются явно для организации-покупателя; пустой список не означает рассылку всем каналам. Тестовые события отделены от рабочих. Можно извлечь общую низкоуровневую SMTP-отправку, но шаблоны и правила маршрутизации должны быть новыми, без ссылки, позволяющей контрагенту отметить счёт оплаченным.

Worker забирает задания атомарно, имеет срок захвата, восстановление после падения и повторные попытки с увеличением задержки. Для SMTP-таймаута — проверка неопределённого результата по существующему принципу. Полный payload счёта и секреты в задания доставки не копировать.

Исходящие webhooks для партнёров — этап 2, не условие запуска MVP. При добавлении нужны отдельные подписки, подпись, ID события, документированные повторы и порядок событий, защита от обращения во внутреннюю сеть; партнёр дедуплицирует события и сверяет ревизию.

## 10. Документы, лимиты и эксплуатация

- Использовать серверные случайные имена хранения; оригинальное имя — только метаданные. Проверять размер, расширение и сигнатуру; запретить HTML, SVG и архивы.
- Начальные предлагаемые лимиты: до 10 МБ на файл, до 5 файлов на счёт, до 30 МБ суммарно. Ограничить поток ещё при чтении и на reverse proxy, а не только после полного приёма тела.
- Сначала писать файл во временное/закрытое хранилище, затем фиксировать метаданные и состояние готовности; счёт нельзя отправить без готового основного документа. Файловая система и БД не имеют общей транзакции — предусмотреть восстановление и уборку зависших/осиротевших файлов с безопасным сроком хранения.
- Проверку файла на вредоносное содержимое предусмотреть отдельным шагом; до успешной проверки документ не выдаётся сотруднику и не допускает отправку счёта. Выбрать и включить проверяющий сервис до промышленного приёма произвольных документов.
- Выдавать документы через авторизованный download с `Content-Disposition: attachment`, `nosniff`; не публиковать каталог хранения и не скачивать документы по произвольным URL партнёра.
- Предлагаемые стартовые квоты, уточняемые на пилоте: 60 чтений/минуту и 20 изменений/минуту на партнёра; отдельные лимиты объёма загрузок/сутки. Счётчики должны работать между экземплярами API — хранилище БД или инфраструктурный gateway, не память одного процесса. Отдельный общий лимит невалидных ключей по источнику.
- Логи: `request_id`, ID партнёра/ключа/счёта, маршрут, результат, длительность. Не писать `Authorization`, тела документов и полные банковские реквизиты.
- Метрики: частота 4xx/5xx/429, задержка API, возраст необработанных событий, число зависших загрузок, ошибки worker. Уведомлять о накоплении очереди и повторяющихся сбоях.
- Резервировать БД и файлы; проверить восстановление связанной пары. Время — UTC, бизнес-даты — календарные даты; правила срока оплаты явно описать в документации.
- Дать B2B отдельную OpenAPI-схему с примерами и описанием ошибок/идемпотентности. Не включать в неё внутренние административные endpoints. CORS и Origin-проверки не заменяют API-авторизацию; для серверного API CORS не требуется. Область действия текущих middleware проверить отдельно, сохранив защиту cookie-маршрутов.

## 11. План работ и проверяемые результаты

### Этап 1. Контракт и миграции

Зафиксировать JSON-схемы, статусы, ошибки, бизнес-ограничения и опубликованный пример интеграции. Добавить организации, партнёров, реквизиты, ключи, счета, документы, историю, идемпотентность и outbox. Текущая цепочка миграций заканчивается `0008`; новые ревизии создавать от актуальной головы на момент разработки.

Готовность: миграции применяются на пустой и заполненной БД, существующие счета и уведомления работают без изменения поведения.

### Этап 2. Машинный доступ

Реализовать выпуск, ротацию, отзыв ключей, привязку к партнёру/окружению, scopes, квоты и аудит. Добавить внутреннее управление партнёрами и разрешениями на покупателя.

Готовность: заблокированный партнёр и отозванный ключ не работают; чужие счета, документы и связи недоступны при любом способе обращения.

### Этап 3. Создание и отправка счетов

Реализовать черновики, валидацию, загрузки, снимки реквизитов, отправку, отзыв, чтение и пагинацию. Все команды — с защитой от дублей и конкурентных изменений.

Готовность: последовательность «создать → PDF → отправить → получить статус» проходит; повторные и одновременные запросы не создают второй счёт или второе событие.

### Этап 4. Обработка нашей компанией

Добавить внутренний реестр и решения, учёт/исправление оплаты, историю, outbox-worker и явно адресованные внутренние уведомления.

Готовность: контрагент видит решение; не может принять или оплатить свой счёт; сбой SMTP не теряет счёт и не блокирует его обработку.

### Этап 5. Документация, пилот, выпуск

Выпустить отдельную OpenAPI, руководство партнёра и примеры curl для всего сценария. Подготовить тестового партнёра и test-ключ, прогнать пилот, настроить метрики и оповещения. Включать доступ сначала одному контрагенту.

Готовность: интеграция проходит с внешнего клиента по документации, восстановление после таймаута/перезапуска проверено; есть рабочие отзыв ключа, блокировка партнёра и выключатель новых B2B-команд без остановки внутреннего API.

Порядок релиза: совместимые миграции → код с B2B-доступом, выключенным флагом → организация и партнёр → тестовый сценарий → включение пилота. При откате выключать новый API, сохраняя записи; не удалять поступившие счета обратной миграцией.

## 13. Обязательные проверки

- Авторизация: истёкший/отозванный ключ, блокировка партнёра, недостаточный scope, подмена окружения.
- Изоляция: чтение, редактирование, список, история, документы и банковские счета другого партнёра; внутренние маршруты не принимают партнёрские ключи.
- Идемпотентность: одинаковый запрос, другой payload с тем же ключом, другая операция с тем же ключом, ротация ключа, истечение хранения ответа, постоянный дубль `external_id`.
- Сбои: падение до/после commit, повтор после потери ответа, сбой файлового хранилища и проверяющего сервиса, перезапуск worker, неопределённый исход SMTP.
- Конкурентность на PostgreSQL: создание одного счёта, отправка и изменение документа, принятие и отзыв, фиксация оплаты и отмена. SQLite для этих гарантий недостаточно.
- Бизнес-правила: нельзя отправить без проверенного PDF, изменить принятые реквизиты, оплатить непринятый или отменённый счёт; причины решений и исправлений обязательны.
- Суммы и даты: Decimal без float, максимум разрядности, точность до копеек, валюта MVP, дата счёта не позже срока; просроченный входящий счёт допустим, но явно отмечается.
- Документы: подмена MIME/расширения, превышение размера и суммарной квоты, опасное имя, чужой документ, непроверенный файл, повторная загрузка.
- Регрессия: существующие разовые/регулярные счета, email, Telegram, публичные ссылки, бюджет, авторизация и миграции сохраняют поведение.

## 14. Решения, которые нужно закрепить перед реализацией

Предложения по умолчанию уже отражены в плане; это точки согласования продукта, а не препятствия к подготовке контракта.

1. Какие реквизиты нашей организации публикуются и кто подтверждает реквизиты контрагента.
2. Достаточно ли admin для принятия/оплаты в MVP или сразу нужна отдельная роль бухгалтерии.
3. Когда входящий счёт должен попадать в общий бюджет — при поступлении или после принятия. До решения вести отдельный реестр.
4. Подтвердить стартовые ограничения: RUB, один PDF счёта, полная ручная отметка оплаты, без строк товаров и расчётов НДС.
5. Нужны ли партнёру push-уведомления уже в первой версии; базовый план использует чтение статуса через GET.
6. Утвердить сроки хранения документов, истории, полных idempotency-ответов и квоты по итогам пилота.

Рекомендуемый порядок реализации: контракт и данные → партнёры/ключи → идемпотентное создание и документы → внутреннее согласование/учёт оплаты → уведомления, документация и пилот.
